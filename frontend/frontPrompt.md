## Промпт для Frontend Engineer

Выступи как Senior Frontend Engineer и Product Designer. Реализуй frontend MVP SupplyLens для хакатона.

## 1. Ограничения

* Стек: React, Vite, TypeScript, Tailwind CSS.
* Используй существующую структуру репозитория.
* Работай только во frontend-части. Не изменяй backend.
* Не добавляй авторизацию, роли, настройки аккаунта и административные страницы.
* Не рассчитывай прогноз во frontend.
* Все числа должны приходить от Go API.
* Не создавай тяжёлую дизайн-систему.
* Интерфейс должен быть полностью готов для записи демо-видео.
* Основной приоритет — desktop 1440×900, но базовая адаптивность обязательна.
* Используй русский язык.
* Не показывай функции, которых нет в API.
* Сначала изучи текущий проект и сохрани существующие настройки.

## 2. Назначение интерфейса

Пользователь — менеджер отдела закупа.

Основной сценарий:

```text
Загрузка Excel
→ проверка данных
→ параметры расчёта
→ получение рекомендаций
→ просмотр причин
→ ручное подтверждение
→ экспорт заказа
```

Интерфейс должен показывать три решения:

```text
BUY      → Заказать
NO_BUY   → Не заказывать
REVIEW   → Проверить вручную
```

## 3. Структура страницы

Сделай одно приложение с четырьмя последовательными состояниями:

1. `IMPORT`
2. `CONFIGURE`
3. `RESULTS`
4. `APPROVED`

Не делай сложную маршрутизацию. Для MVP достаточно одной основной страницы.

## 4. Экран импорта

Покажи шесть обязательных файлов:

* MOQ;
* детальные продажи;
* ежемесячные остатки;
* ежемесячные продажи;
* сезонность;
* товар в пути.

Для каждого файла покажи:

* название;
* выбранный файл;
* размер;
* состояние `Не выбран / Готов / Загружается / Ошибка`.

Добавь:

* drag-and-drop;
* обычный file picker;
* кнопку `Загрузить и проверить`;
* кнопку `Использовать демо-данные`, если backend поддерживает demo dataset;
* общий прогресс;
* сообщение, что файлы не отправляются поставщику.

Используй:

```http
POST /api/v1/import
```

После успеха покажи:

```text
497 товаров найдено
467 товаров полностью сопоставлено
30 товаров требуют проверки
```

Предупреждения импорта должны быть видимыми, но не блокировать переход, если backend считает dataset пригодным.

## 5. Настройки расчёта

Создай компактную панель:

```text
Поставщик: SystemElectric
Срок поставки: 30 дней
Страховой запас: 14 дней
```

Дополнительные переключатели:

* учитывать остаток витрины;
* учитывать остаток ТЗ;
* учитывать розничный склад;
* использовать NVIDIA для проверки аномалий;
* использовать OpenAI для объяснений.

Основная кнопка:

```text
Рассчитать заказ
```

Запрос:

```http
POST /api/v1/runs
```

```json
{
  "datasetId": "dataset-001",
  "supplier": "SystemElectric",
  "leadTimeDays": 30,
  "safetyDays": 14,
  "includeShowcase": false,
  "includeTZStock": false,
  "includeRetailStock": false,
  "useNvidiaReview": true,
  "useOpenAIExplanation": true
}
```

Во время расчёта покажи этапы:

```text
Анализ продаж
Поиск аномалий
Учёт сезонности и stockout
Расчёт заказа
Подготовка объяснений
```

Не показывай выдуманный процент, если backend не отдаёт реальный progress.

## 6. Экран результатов

Верхняя часть должна содержать KPI:

* позиций заказать;
* не требуется заказ;
* требуют проверки;
* общее количество единиц;
* ориентировочная стоимость.

Под KPI размести:

* поиск по названию, артикулу или коду 1С;
* фильтр решения;
* фильтр категории;
* фильтр срочности;
* переключатель `Только с предупреждениями`.

## 7. Основная таблица

Колонки:

```text
Товар
Код 1С
Артикул
Категория
Свободный остаток
В пути
Прогноз
Рекомендация
Стоимость
Срочность
Решение
```

Цвета статусов:

* `BUY` — спокойный синий;
* `NO_BUY` — нейтральный серый или зелёный;
* `REVIEW` — янтарный;
* критическая срочность — красный только как акцент.

Не окрашивай всю таблицу яркими цветами.

Показывай товары, сгруппированные под поставщиком `SystemElectric`.

По умолчанию сортируй:

1. `REVIEW`;
2. критичные `BUY`;
3. остальные `BUY`;
4. `NO_BUY`.

Добавь понятные пустые состояния.

## 8. Drawer «Почему такое количество?»

При нажатии на строку открой правую панель.

В верхней части:

```text
Название товара
Код 1С
Решение
Рекомендуемое количество
Ориентировочная стоимость
```

Далее покажи формулу:

```text
Базовый спрос                 100
Сезонность ×                  1,12
Рост ×                        1,05
Stockout-компенсация          +15
Страховой запас               +20
Свободный остаток             −35
Товар в пути                  −40
─────────────────────────────────
Расчётная потребность          85
Кратность                      10
Рекомендуемый заказ            90
```

Не вычисляй её повторно. Используй `breakdown` из API.

## 9. График Demand X-Ray

Используй Recharts или уже установленную библиотеку.

Покажи:

* месячные продажи;
* очищенный спрос;
* прогноз;
* периоды stockout;
* крупную аномальную операцию;
* подпись неполного сентября 2026.

Если данных для графика нет, покажи понятное состояние, а не пустой график.

## 10. AI-анализ аномалии

Если NVIDIA обнаружила кандидата, покажи отдельный блок:

```text
Проверка NVIDIA

Классификация: вероятно разовая продажа
Продажа: 420 шт.
Обычный заказ: около 10 шт.
Доля в месяце: 99,8%
Уверенность: высокая

Причина:
Операция значительно превышает обычный размер и не повторяется регулярно.
```

Кнопки менеджера:

```text
Исключить из регулярного спроса
Считать регулярным спросом
Оставить на проверку
```

Используй:

```http
PATCH /api/v1/runs/{runId}/items/{code1C}
```

После ответа обнови строку, breakdown и KPI из ответа backend.

Не давай пользователю подтверждать аномалию, если API не вернул необходимые данные.

## 11. OpenAI-объяснение

Покажи блок:

```text
Вывод для закупщика
```

Содержимое:

* короткий итог;
* 2–5 причин;
* предупреждения;
* метка источника: `AI explanation` или `Системное объяснение`.

Не выводи технический prompt, токены или сырой JSON.

## 12. Ручная корректировка

Добавь поле:

```text
Утверждённое количество
```

Рядом показывай:

```text
Рекомендация системы: 90
```

Правила:

* только целое неотрицательное число;
* если значение не соответствует MOQ, показать предупреждение;
* не исправлять значение молча;
* сохранить комментарий менеджера;
* явно показать, что количество изменено вручную.

Кнопка:

```text
Сохранить решение
```

## 13. Предупреждения о данных

Показывай предупреждения backend:

* неполный текущий месяц;
* отсутствует MOQ;
* недостаточно истории;
* конфликт месячных и детальных продаж;
* аномалия требует подтверждения;
* не удалось получить AI-review;
* стоимость неизвестна.

`REVIEW` нельзя визуально выдавать за готовый заказ.

## 14. Подтверждение и экспорт

Внизу результатов сделай sticky action bar:

```text
Выбрано к заказу: 25 позиций
Количество: 12 450 единиц
Ориентировочная стоимость: 18 500 000 ₸
```

Кнопка:

```text
Подтвердить и экспортировать CSV
```

Используй:

```http
POST /api/v1/runs/{runId}/approve-export
```

После успеха:

* скачай CSV;
* покажи состояние `Заказ сформирован`;
* не показывай сообщение об отправке поставщику;
* укажи, что файл подготовлен для дальнейшей загрузки в учётную систему.

## 15. API-типы

Создай централизованные TypeScript-типы:

```ts
type Decision = "BUY" | "NO_BUY" | "REVIEW";
type Urgency = "CRITICAL" | "HIGH" | "MEDIUM" | "LOW";

interface RunSummary {
  buy: number;
  noBuy: number;
  review: number;
  totalUnits: number;
  estimatedCost: number | null;
}

interface RecommendationItem {
  code1C: string;
  article: string;
  name: string;
  category: string;
  supplier: string;
  decision: Decision;
  urgency: Urgency;
  recommendedQuantity: number;
  approvedQuantity?: number;
  estimatedCost: number | null;
  breakdown: CalculationBreakdown;
  anomalies: Anomaly[];
  warnings: Warning[];
  explanation: Explanation;
}
```

Вынеси API-вызовы в отдельный модуль:

```text
src/api/supplyLensApi.ts
```

Не размещай `fetch` непосредственно внутри визуальных компонентов.

## 17. UX-состояния

Для каждого API-запроса реализуй:

* loading;
* error;
* retry;
* empty;
* success.

Кнопки должны блокироваться во время повторной отправки.

Ошибки показывай понятным русским текстом.

Не удаляй предыдущий успешный результат из интерфейса при временной ошибке повторного запроса.

## 18. Визуальный стиль

Стиль должен выглядеть как современный B2B-инструмент закупщика:

* светлый фон;
* тёмный текст;
* синий основной акцент;
* компактные таблицы;
* аккуратные границы;
* минимум декоративных элементов;
* хорошая читаемость чисел;
* моноширинный стиль для кодов 1С;
* форматирование чисел через русскую локаль;
* стоимость в тенге, только если она пришла от backend.

Не делай интерфейс похожим на AI-чат.

Главный объект интерфейса — таблица закупочных решений.

## 19. Definition of Done

Frontend готов, когда пользователь может:

1. Выбрать шесть Excel-файлов.
2. Импортировать их.
3. Увидеть результат проверки.
4. Настроить срок поставки и страховой запас.
5. Запустить расчёт.
6. Увидеть `BUY`, `NO_BUY`, `REVIEW`.
7. Открыть детальное объяснение позиции.
8. Увидеть график, stockout и аномалии.
9. Подтвердить или отклонить аномалию.
10. Изменить рекомендуемое количество.
11. Сохранить решение.
12. Экспортировать подтверждённый CSV.

После реализации:

* запусти доступный lint;
* запусти TypeScript typecheck;
* запусти тесты, если они настроены;
* выполни production build;
* исправь обнаруженные ошибки;
* сообщи, какие файлы изменены;
* перечисли реализованные сценарии;
* отдельно укажи ограничения и незавершённые функции.

Не реализуй backend-логику на frontend и не подменяй реальные API-вызовы статическими результатами, кроме явно отделённого demo/mock режима.
