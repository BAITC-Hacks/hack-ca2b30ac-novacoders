# SupplyLens backend MVP

Go 1.26.1+, один HTTP-процесс, XLSX через Excelize, dataset и runs в памяти.
Backend отвечает за импорт, детерминированные расчёты, решения менеджера и CSV.
AI вынесен за его пределы: внешний сервис может читать готовые факты через
`GET /api/v1/runs/{runId}`. В backend нет AI-клиентов и генерации объяснений.

## Запуск

Из корня репозитория:

```bash
cd backend
go mod download
go run ./cmd/api
```

Проверка: `curl http://127.0.0.1:8080/healthz` → `{"status":"ok"}`.
SIGINT/SIGTERM запускает graceful shutdown. Перезапуск удаляет datasets, runs и
одобрения. JSON-персистентность в этом MVP не включена.

Конфигурация читается только из environment; `.env` автоматически не загружается.
API-ключи для запуска не нужны. Подозрительные операции остаются на ручной проверке.

| Переменная | Значение по умолчанию |
|---|---|
| `HTTP_ADDR` | `127.0.0.1:8080` |
| `CORS_ORIGINS` | `http://localhost:5173,http://127.0.0.1:5173,http://localhost:3000,http://127.0.0.1:3000` |

`CORS_ORIGINS` — список точных origin через запятую. Для доступа с другого
устройства явно задайте `HTTP_ADDR=0.0.0.0:8080`. Авторизация пользователей в MVP
отсутствует; сервер предназначен для локальной демонстрации.

## Импорт

`POST /api/v1/import`, `multipart/form-data`, ровно по одному XLSX в каждом поле:

| Поле | Обязательные заголовки |
|---|---|
| `moq` | `Номенклатура.Код`, `Артикул`, `Кратность` |
| `sales_transactions` | `Дата`, `Номер`, `Документ`, `Код`, `Номенклатура`, `Склад`, `Количество` |
| `monthly_stock` | `Номенклатура.Код` и месячные колонки |
| `monthly_sales` | `Номенклатура.Код`, `Артикул` и месячные колонки |
| `seasonality` | `Месяц` / `Месяцы`, `Общий коэффициент сезонности` / `Коэффициент сезонности` |
| `in_transit` | `Артикул поставщика`, `Код 1с`, `Наименование`, `Категория 2026`, `СС реал`, `Витрина`, `Остаток ТЗ`, `Розничный склад`, `Остаток`, `Зарезервировано`, `Свободный остаток`, `Заказ`, `СЭ в пути 24.09` |

Имя файла произвольное; используется первое найденное соответствие обязательным
заголовкам в первых 30 строках листов книги. Поддерживаются переносы строк,
неразрывные и повторные пробелы в заголовках; месяц `2026-08`, `08.2026`,
`Август 2026`, Excel-дата, а также отдельная строка годов над месяцами.
Таблица сезонности — строки месяцев 1–12 или их названий с числовым коэффициентом.

Коды соединяются только как строки: `030200128_` сохраняется целиком. Формат
ячейки с ведущими нулями сохраняется; если Excel уже сохранил код обычным числом
без такого формата, восстановить потерянные нули невозможно. Даты Excel 1900/1904
поддерживаются. Десятичная запятая, пробелы-разделители и отрицательные возвраты
сохраняются. `Номер` используется как document ID, при пустом номере — `Документ`.

Ноль в месячных продажах — известное значение. Пустые продажи перечислены в
`blankSalesMonths`; отсутствующие месяцы отсутствуют в карте. Для исторического
остатка пустая ячейка — `null`, отсутствующая колонка — отсутствующий ключ.
Текущие поля отслеживаются через `presentFields`: пустой `freeStock` или
`inTransit` не считается известным нулём. `Заказ` не прибавляется к товару в пути.
`СС реал` трактуется как ориентировочная себестоимость единицы.

Итоговые строки пропускаются с отдельным счётчиком. Ошибка отдельной ячейки или
строки включается в диагностику; остальные строки обрабатываются. Дубликат SKU
в недетальном источнике не суммируется: сохраняется первая строка и блокирующее
предупреждение. Некорректная книга или отсутствие обязательных заголовков даёт
422, dataset не сохраняется. Исходные XLSX после запроса не хранятся.

Ответ 201:

```json
{
  "datasetId": "dataset-001",
  "products": 4,
  "fullyMatchedProducts": 4,
  "warnings": [{"code":"PARTIAL_CURRENT_MONTH","message":"..."}],
  "diagnostics": {
    "processedRows": {},
    "skippedTotalRows": {},
    "uniqueProducts": 4,
    "fullyMatchedProducts": 4,
    "productsWithoutMOQ": ["030200130_"],
    "productsWithoutSales": [],
    "productsWithoutCurrentStock": [],
    "sourceConflicts": [],
    "warnings": [],
    "errors": []
  }
}
```

`fullyMatchedProducts` означает наличие SKU во всех пяти товарных источниках;
качество значений оценивается отдельно. `GET /api/v1/datasets/{datasetId}`
возвращает ту же сводку и диагностику.

## Расчёт и интерпретация

`POST /api/v1/runs`, `Content-Type: application/json`:

```json
{
  "datasetId": "dataset-001",
  "supplier": "SystemElectric",
  "leadTimeDays": 30,
  "safetyDays": 14,
  "includeShowcase": false,
  "includeTZStock": false,
  "includeRetailStock": false
}
```

`datasetId`, `supplier`, `leadTimeDays` обязательны; lead time 1–365 дней,
safety 0–365. Пропущенные boolean-поля равны false, safety — 0.
Ответ 201: `runId`, `datasetId`, `createdAt`, `config`, `summary`, `items`.
`GET /api/v1/runs/{runId}` возвращает сохранённый результат.

После отделения AI поля запроса `useNvidiaReview`, `useOpenAIExplanation` удалены:
их передача, как и других неизвестных полей, даёт 400. Из ответа удалены
`explanation`, `aiReview`, `aiReviewStatus`. Числовая раскладка, детерминированные
кандидаты на аномалии и предупреждения доступны внешнему сервису в этом же API.

Каждая позиция содержит `code1C`, `article`, `name`, `supplier`, `decision`,
`urgency`, `recommendedQuantity`, `approvedQuantity`, `finalQuantity`,
`estimatedCost`, `unitCost`, `breakdown`, `anomalies`, `warnings`,
`managerComment`. `estimatedCost: null` означает отсутствие положительной цены.

Алгоритм пакета `internal/forecast`:

1. Дата среза фиксирована: **22.09.2026**. Последние 12 полных месяцев:
   **2025-09…2026-08**. Сентябрь 2026 никогда не входит в базовый спрос,
   рост или обучение сезонности.
2. Базовый спрос — медиана известных очищенных продаж марта–августа 2026,
   **разделённых на сезонный коэффициент соответствующего месяца**. Это
   устраняет повторное применение сезонности к уже сезонным наблюдениям.
   Пропущенный месяц не подменяется нулём; неполные шесть месяцев дают `REVIEW`.
   Отрицательные продажи остаются в dataset, но для прогноза ограничены нулём.
3. Рост — сумма июня–августа 2026 / сумма июня–августа 2025, ограничение
   0.5…1.5. Используется история после восстановления stockout. При неполном
   сравнении или нулевом знаменателе — 1 и предупреждение.
4. Сезонность SKU: среднее продаж календарного месяца / среднее 12 календарных
   средних. Каждому месяцу даётся одинаковый вес, даже если история содержит
   неполные годы. Требуются минимум два наблюдения каждого из 12 месяцев;
   диапазон 0.25…3. Иначе используется общий коэффициент, затем 1 с
   предупреждением. Коэффициенты взвешиваются по фактическим дням горизонта
   от даты среза; 30 дней с 22 сентября = 9 дней сентября и 21 день октября.
5. Stockout рассматривается только для явно пустого/нулевого остатка, известной
   продажи и активности до и после в пределах двух месяцев. Нет записи об
   остатке — нет автоматического stockout. Такой консервативный подход исключает
   начальные и конечные пробелы новых/выводимых SKU. Восстановление — тот же
   месяц прошлого года, иначе медиана соседних активных месяцев. Отрицательные
   продажи не восстанавливаются как stockout: это могут быть возвраты.
   Сезонность и рост считаются по восстановленной истории. Базовые медианы до
   и после восстановления используют один и тот же сезонный профиль.
   `stockoutCompensation = max(0, restoredBase - baseMonthlyDemand) × seasonFactor × growthFactor × targetMonths`.
   Если медиана уже компенсировала одиночный нулевой месяц, добавка равна 0,
   а период всё равно указан в `stockoutPeriods`. Например, для базовых продаж
   `[100,100,0,100,100,100]` прогноз остаётся 100; для трёх подтверждённых
   пропусков медиана 50 восстанавливается до 100, компенсация — 50 при единичных
   коэффициентах и месячном горизонте.
6. Доступно = `freeStock + inTransit` + явно включённые дополнительные остатки.
   `totalStock` и `reservedStock` повторно не прибавляются и не вычитаются.
   Перед включением дополнительных складов менеджер должен знать, входят ли
   они уже в свободный остаток.
7. `targetMonths = leadTimeDays / 30`.
   `forecastDemand = baseMonthlyDemand × seasonFactor × growthFactor × targetMonths + stockoutCompensation`.
   `safetyStock = restoredBase × safetySeasonFactor × growthFactor × safetyDays / 30`.
   `safetySeasonFactor` взвешивает месяцы **после окончания lead time**:
   с даты `asOf + leadTimeDays` на протяжении `safetyDays`. Резерв добавляется
   **один раз**, отдельно от lead time; оба горизонта непересекающиеся.
   `rawNeed = max(0, forecastDemand + safetyStock - available)`.
   `recommendedQuantity = ceil(rawNeed / orderMultiple) × orderMultiple`.
   Округление строго вверх, без вычитания epsilon: количество покрывает rawNeed.
   При неизвестной кратности количество остаётся 0 с `REVIEW`, а `rawNeed`
   показывает предварительную потребность; единица не подставляется.
8. `BUY` — положительное количество без блокирующих предупреждений; `NO_BUY` —
   ноль при достаточных данных; `REVIEW` — конфликт, неизвестная кратность,
   история/текущий остаток/товар в пути или неподтверждённая аномалия.
   `urgency=HIGH`, когда собственный свободный остаток не покрывает lead time;
   иначе для заказа/проверки MEDIUM, для достаточного запаса LOW.

`summary` содержит `buy`, `noBuy`, `review`, `totalUnits`, `estimatedCost`,
`unpricedItems`, `approvedItems`. Суммы включают все предварительные позиции
и используют `finalQuantity`; это не сумма только утверждённого заказа.

## Аномалии

Детальные операции группируются по SKU + document ID + месяц с учётом возвратов.
Кандидат: `quantity > max(Q3 + 3×IQR, median×5)`, доля месячных продаж ≥ 0.5,
не более двух событий хотя бы половины размера кандидата. Регулярные крупные
партии сохраняются. Кандидаты ищутся только в полных месяцах.

Сверка месячных и детальных сумм использует допуск 1%, минимум 0.01 единицы.
Сравниваются только месяцы с детальными операциями. Отсутствующий месячный
источник или расхождение даёт `SOURCE_CONFLICT` и `REVIEW`; операции не
исключаются. Отсутствие детальных операций само по себе не означает нулевой спрос.

Автоматического исключения нет. До явного решения менеджера кандидат даёт
`REVIEW` / `UNCONFIRMED_ANOMALY`. `EXCLUDE` удаляет операцию из расчётной истории
только при согласованных источниках; `KEEP` оставляет её в спросе. Согласованность
повторно проверяется при пересчёте. Исходный dataset не изменяется.

## Решение менеджера и CSV

`PATCH /api/v1/runs/{runId}/items/{code1C}`:

```json
{
  "approvedQuantity": 100,
  "anomalyDecision": "EXCLUDE",
  "comment": "Крупный проектный заказ подтверждён как разовый"
}
```

Поля необязательны, но хотя бы одно обязательно. `approvedQuantity` — целое число
0…1e12, явно подтверждающее количество; 0 означает отказ от заказа.
`anomalyDecision` = `EXCLUDE` или `KEEP` применяется ко **всем кандидатам позиции**;
поле нельзя передавать товару без кандидатов. `EXCLUDE` действует только при
согласованных источниках. `KEEP` сохраняет операцию и снимает неопределённость
аномалии, но не скрывает конфликт или прочие проблемы данных.

Позиция и summary пересчитываются атомарно. `recommendedQuantity` сохраняет
математическую рекомендацию; `finalQuantity` равен одобренному количеству, если
оно есть. `decision` остаётся оценкой расчёта и качества данных, а факт одобрения
отражается отдельно. Ручное количество может нарушать MOQ с предупреждением.
Изменение решения об аномалиях сбрасывает прежнее одобрение, если новое количество
не передано в том же PATCH. Изменение только комментария сохраняет одобрение.

`POST /api/v1/runs/{runId}/approve-export` возвращает UTF-8 CSV:

```csv
supplier,code_1c,article,name,quantity,estimated_cost,decision,manager_comment
```

Экспортируются только явно подтверждённые количества > 0, включая позиции,
которые менеджер подтвердил несмотря на `REVIEW`. Вызов экспорта сам не одобряет
позиции и ничего не отправляет поставщику. Пустой экспорт содержит только
заголовок. Неизвестная цена — пустое поле. Текстовые формулы экранируются;
при открытии CSV в Excel импортируйте колонку `code_1c` как текст.

## Demo flow

В одном терминале запустите API. В другом, из `backend/`:

```bash
go run ./cmd/demo

curl --fail-with-body -sS http://127.0.0.1:8080/api/v1/import \
  -F 'moq=@data/demo/MOQ SystemElectric.xlsx' \
  -F 'sales_transactions=@data/demo/Динамика продаж_Syseme Electric_2025-2026.xlsx' \
  -F 'monthly_stock=@data/demo/Ежемесячные остатки SystemElectric 2024-2026.xlsx' \
  -F 'monthly_sales=@data/demo/Ежемесячные продажи в кол-м выражении SystemElectric 2024-2026.xlsx' \
  -F 'seasonality=@data/demo/Сезонность SystemElectric 2024-2026.xlsx' \
  -F 'in_transit=@data/demo/Товар в пути_SystemElectric на 22.09.2026.xlsx'

# На свежем процессе это dataset-001. Для последующих импортов подставьте ID ответа.
curl --fail-with-body -sS http://127.0.0.1:8080/api/v1/runs \
  -H 'Content-Type: application/json' \
  -d '{"datasetId":"dataset-001","supplier":"SystemElectric","leadTimeDays":30,"safetyDays":14}'

# Аналогично используйте runId из ответа; на свежем процессе это run-001.
curl --fail-with-body -sS -X PATCH \
  http://127.0.0.1:8080/api/v1/runs/run-001/items/030200128_ \
  -H 'Content-Type: application/json' \
  -d '{"approvedQuantity":100,"comment":"Подтверждено менеджером"}'

curl --fail-with-body -sS -X POST \
  http://127.0.0.1:8080/api/v1/runs/run-001/approve-export \
  -o data/demo/approved.csv
```

Синтетический набор содержит 4 SKU: один BUY, один NO_BUY, один REVIEW без MOQ,
один REVIEW с крупной разовой продажей. Экспорт после PATCH содержит один SKU.
`data/demo/` игнорируется Git. Эти файлы не являются реальными данными заказчика.

## Ошибки, лимиты и проверки

Единый ответ ошибки:

```json
{"error":{"code":"INVALID_INPUT","message":"...","details":{}}}
```

Коды HTTP: 400 — неверный запрос; 403 — запрещённый CORS origin;
404 — неизвестный ресурс; 405 — метод; 413 — размер; 415 — Content-Type;
422 — структура XLSX (`details` содержит диагностику); 408/504 — отмена/таймаут.
Лимиты: 20 MiB на файл, 121 MiB на multipart, 128 MiB распакованной книги,
250 000 строк на лист, 1 MiB JSON. `NaN`, бесконечность и числа > 1e12 во входных
ячейках отвергаются. Таймаут обработки запроса — 60 секунд.
Логи содержат этапы, идентификаторы расчётов и счётчики,
без ключей, исходных Excel, названий товаров или комментариев менеджера.

```bash
gofmt -w cmd internal
go test ./...
go test -race ./...
go vet ./...
go build ./...
```

Тесты проверяют спрос, рост, сезонность, stockout без двойного учёта, границы
округления MOQ, остатки, стоимость и summary, аномалии и конфликты источников,
генерацию и чтение шести XLSX, полный HTTP import → run → patch → export,
отмену контекста, конкурентные записи, изоляцию хранилища, CORS и защиту CSV.

Реальные шесть XLSX не приложены к репозиторию/заданию, поэтому их конкретные
листы и форматирование пока не проверены. Необычный многоуровневый отчёт или
горизонтальная таблица сезонности могут потребовать адаптации импортера.
Прогноз — прозрачные MVP-эвристики, а не обученная модель; долгосрочное хранение,
авторизация и отправка поставщику не реализованы.
