## Конфигурация и lifecycle

Обновлены `AGENTS.md`, `.env.example`, `app/settings.py`, README и контракт. Исторические `audit.md` и `implementation.md` сохранены с заметками о переходе.

`OPENAI_API_KEY` один для двух задач. Для analysis выбирается непустой `OPENAI_ANALYSIS_MODEL`, иначе `OPENAI_MODEL`; для explanation аналогично `OPENAI_EXPLANATION_MODEL`. Пробелы по краям удаляются; пустое переопределение означает базовую модель. При 401/403/404 модель не меняется.

Устаревшие настройки: `NVIDIA_API_KEY`, `NVIDIA_MODEL`, `NVIDIA_BASE_URL`. Они удалены из настроек и примера окружения, не нужны для запуска и игнорируются, если остались в окружении. Их наличие в настоящем `.env` не проверялось.

Один `ProviderClients` создаётся в lifespan приложения и закрывает свой AsyncOpenAI при завершении. SDK-клиент создаётся только при live + ALLOW_EXTERNAL_AI + непустом ключе; при отсутствии ключа вызов возвращает not_configured. В mock SDK-клиент не создаётся. Анализ и будущие объяснения используют общий клиент и семафор, максимум 2 вызова на процесс по умолчанию.

Endpoint жёстко задан: `https://api.openai.com/v1`. `OPENAI_BASE_URL` не используется; произвольный URL из JSON невозможен. HTTP-прокси окружения и следование редиректам отключены.

Вызов: `await client.responses.parse(model=..., instructions=..., input=..., text_format=PydanticModel, store=False, max_output_tokens=...)`. По умолчанию 2048 выходных токенов, общий deadline 15 секунд (очередь + SDK + повторы), 1 повтор только на уровне SDK. Дополнительных циклов повторов и смены модели нет. Tools, temperature, top_p и неподтверждённые параметры не добавлялись.

Проверяется response.status, ошибка/незавершённость, refusal, наличие ровно одного непустого текстового результата и Pydantic-схема. Некорректный JSON может быть отклонён SDK ещё до проверки status; это invalid_response, а не успешный пустой результат. Логи приложения содержат фиксированные коды и тип задачи без exception text, prompts, ответов, ID клиентов и ключей.

## Анализ и контекст

`app/analysis/context.py` строит один контекст SKU + warehouse_id + supplier_id. Имена товаров/поставщиков, стоимость, sourceMeta, пути файлов и Excel в него не попадают. Используются датированные продажи, при их отсутствии месячные продажи, и доступные реальные order rows. Детализация заказов не складывается с агрегированными продажами. Клиентские ID дополнительно псевдонимизируются SHA-256 с префиксом client_. Это псевдонимизация, не обещание необратимой анонимности.

Для устранения коллизий источники имеют стабильные namespace ID: `sales:<row_id>`, `order:<transactionId>`, `month:<YYYY-MM>`, `stockout:<start>:<end>`. Исходный ID хранится отдельно в source_row_id. Для месячных агрегатов и интервалов ID производный, не выдаётся за существующий transactionId. Артикулы и SKU не преобразуются в числа.

По умолчанию передаются до 120 наиболее свежих evidence rows с сохранением хотя бы одной строки основного ряда продаж, если он есть; truncation и размер исходного набора указаны явно. Статистика вычисляется по сохранённому окну: число известных/неизвестных значений, реальные нули, среднее, медиана, максимум и отношение к положительной медиане. Неизвестные значения не заменяются нулями. Контекст ограничен 65 536 байтами; превышение отклоняется до вызова API. Сезонность включается при наличии; нулевой месячный остаток не превращается в stockout. В evidence попадают только явно переданные интервалы недоступности или положительное число stockoutDays; будущие интервалы исключаются.

`app/prompts/analysis_v1.txt`, версия `analysis-1.0.0`, задаёт различие большого заказа, сезонности и устойчивого роста, ограниченность месячных данных и недоверие к инструкциям во входных строках.

`AnalysisService.analyze_series(context)` возвращает AnalysisResult. ModelAnalysis содержит предложения с evidence_row_ids, anomaly_type, proposed_action, explanation, missing_evidence и явными списками referenced_client_ids/referenced_dates. Лишние поля (включая accepted/status и переписанный dataset) запрещены. Типы и действия ограничены enum и проверкой допустимых пар.

Python проверяет все evidence_row_ids, явные ссылки на клиентов/даты по процитированным строкам, ISO-даты, client_... и row[...] в тексте. Клиентов из другой строки нельзя использовать как подтверждение. Для one-off без клиентской детализации и stockout без подтверждения требуется явно указать недостающие доказательства. Каждое предложение получает статус needs_review; accepted в схеме результата отсутствует. Ни исходные данные, ни аналитическая копия не изменяются.

Свободное объяснение остаётся гипотезой модели: структурная проверка ссылок не доказывает истинность всех естественно-языковых утверждений. Поэтому текст не используется для автоматических корректировок и требует проверки. Не поддерживаются произвольные неструктурированные обозначения людей/дат как доказательства.

Успешный результат без предложений требует явного непустого no_anomalies_reason. Невалидный, пустой, обрезанный ответ, отказ, timeout или ошибка доступа возвращают status=failed с error_code; proposals=[] при ошибке не означает «аномалий нет».

`MockAnalysisProvider` возвращает явно демонстрационное предложение по существующей строке. Результат помечен source=mock, is_demo=true; оно не утверждает, что реальная аномалия найдена.

## Граница выполненного этапа

Сервис анализа создаётся в lifecycle как `app.state.analysis_service`; build_context и analyze_series готовы для следующего этапа pipeline. Это внутренняя точка интеграции, не новый HTTP endpoint. Существующий POST recommendations по-прежнему возвращает прежний synthetic mock; live — явный 503 до реализации настоящего расчёта и объяснения. Общий клиент уже поддерживает выбор explanation-модели и Structured Outputs, но отдельный explanation service не реализовывался этим поручением.

Внешние старые поля сохранены через alias/compat.py и всегда обозначают неиспользование прежнего провайдера. Результаты OpenAI не подписываются старым провайдером. Полный live-ответ потребует согласованного расширения/адаптера; текущие HTTP-примеры сохранены без изменения.
