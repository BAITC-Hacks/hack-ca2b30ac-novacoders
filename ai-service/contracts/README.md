# Контракт сервиса

Основа — корневой `alibekAI.md`. Сохранены `GET /health`, `POST /v1/recommendations`, camelCase-поля запросов и ответов, `code1C`, `action`, `calculation`, структура summary, статусы провайдеров и формат ошибок. Исходный документ не изменялся. Работает Python baseline с mock/live analysis и explanation; расширения ниже нужно передать владельцу Go-backend для согласования перед live-интеграцией.

Исполняемые схемы: `app/schemas.py`; OpenAPI доступен на `/openapi.json` после авторизации. `request.example.json` и `response.example.json` — синтетические примеры, проверяемые этими же моделями в pytest. Ответ сохранён из текущего Python-pipeline; тест сравнивает его с pipeline, исключая время и ID запуска.

## Версии и совместимость

- Принимаются `schemaVersion: "1.0"` (исходный формат) и `"1.1"` (его расширение). Версия возвращается в ответе. Реализация принимает добавленные поля и для 1.0, чтобы миграция была постепенной; 1.1 обозначает договорённость об их использовании, отдельной несовместимой схемы нет.
- Вход поддерживает snake_case: `request_id`, `schema_version`, `as_of_date`, `warehouse_id`, `supplier_id`, `row_id` и остальные имена Python-полей. `sku` — alias для `code1C`. Ответ сохраняет camelCase; исключение — явно требуемый флаг `is_demo`.
- Не передавайте два alias одного поля одновременно: лишние/неизвестные поля запрещены, чтобы опечатки не пропадали молча.
- `products` обязателен и непустой. Обязательны `schemaVersion`, UUID `requestId` и `asOfDate`. Настройки имеют видимые в OpenAPI defaults; дополнительные источники необязательны.
- Идентификаторы и артикулы — строки: `"000317_"` не преобразуется в число, `_` не удаляется. Неизвестные числовые значения сохраняются как `null`, не как 0. Отрицательные продажи допустимы; NaN и бесконечности запрещены.

## Дополнения к входу

| Поле | Смысл |
| --- | --- |
| `products[].warehouseId`, `supplierId` | Вместе с `code1C` образуют уникальный ключ товара |
| `products[].unit` | Единица всех количеств данного товара |
| `products[].minimumOrderQuantity` | Минимальное количество положительного заказа, допускает 0 и null |
| `products[].orderMultiple` | Положительная кратность заказа или null |
| `products[].additionalGrowthRate` | Дополнительный прирост долей: 0.05 = +5%; null = неизвестен |
| `products[].leadTimeDays`, `reviewPeriodDays` | Необязательные параметры позиции; общие значения есть в settings |
| `salesHistory[]` | Датированные продажи с обязательным стабильным `rowId`, `date`, `quantity` и ключом товара |
| `inventory[].stockAsOfDate` | Дата актуальности остатка; отсутствие остаётся неизвестным |
| `incomingShipments[]` | Ключ товара, стабильный `rowId`, количество и `expectedDate`; неизвестные количество/дата допускают null |
| `availability[]` | Ключ товара, `startDate`, `endDate`, необязательные `available`, `stockoutDays` |
| `transactions[].clientId` | Необязательный обезличенный ID клиента; ФИО и контакты не передавать |
| `transactions[].transactionId` | Исходное имя стабильного ID; также принимает `rowId`/`row_id` |
| `settings.reviewPeriodDays` | Период пересмотра закупок, по умолчанию 30 дней |

В исходном v1 `moq` назывался MOQ, но означал **кратность**. Эта семантика сохранена: `moq` — устаревающее поле кратности, **не минимум заказа**. Новые отправители должны использовать `minimumOrderQuantity` и `orderMultiple`. Если одновременно заданы `moq` и `orderMultiple`, они должны совпадать. Минимум заказа никогда не выводится из старого `moq`.

`seasonality[]` сохраняет исходную глобальную помесячную структуру: месяц 1–12, коэффициент >= 0 или null. Отсутствующие месяцы не заполняются нулями. Коэффициенты категорий/товаров пока не определены. Месячный остаток сам по себе не трактуется как длительность stockout.

Для старых запросов warehouseId/supplierId могут отсутствовать (остаются null). Строка истории без этих ID допустима, только если однозначно относится к одному товару. При повторении SKU между складами/поставщиками нужно явно указывать ключ в соответствующих строках. Неоднозначные, неизвестные ссылки и дубли товаров/строк/месяцев отвергаются с 422. Имена `warehouse` и `supplier` не подменяют стабильные ID.

`salesHistory` и `transactions` — разные представления данных, их нельзя складывать как независимые продажи. `inventory.inTransit` и `incomingShipments` также нельзя суммировать друг с другом. Приоритет агрегатов: monthlySales, иначе salesHistory, иначе transactions. Подробности не прибавляются к месячным итогам. Для исключения разовых строк сумма детализации должна совпасть с месячным итогом.

## MVP: расчёт и расширения

Маршруты и прежние имена сохранены. Важно для Go: неизвестные `forecast`, `recommendedQuantity`, компоненты расчёта и `summary.totalRecommendedQuantity` теперь могут быть **null**. Не преобразовывайте null в 0. Ошибок HTTP для неполных, но валидных данных нет: позиция получает `action=REVIEW`, `processingStatus=needs_review`, `missingFields`. Summary quantity неизвестна, если неизвестна хотя бы одна позиция; общая сумма количеств разных единиц не является физическим KPI.

Входные необязательные дополнения:

- `is_demo=true` — отправитель маркирует синтетические данные (default false).
- `products[].quantityStep` — допустимый шаг количества. Для штучных единиц без поля используется 1; для остальных единиц шаг нужен явно.
- `confirmedOneOff=true` и непустой `businessReason` у строки monthlySales / salesHistory / transactions — подтверждение бизнеса, а не модели. Go должен принимать такие метки только из доверенного источника.
- `settings.salesHistoryComplete=true` — Go подтверждает полноту разреженной датированной истории за представленные месяцы. Без этого требуется запись за каждый день, иначе количество заказа неизвестно. Месячный агрегат предполагается полным.

`calculationSource=python`: количество всегда рассчитывает Python. В mock — `source=fallback`; в live успешные AI-этапы — `source=live`, при сбоях — `fallback`. `is_demo` на верхнем уровне/позиции отражает метку входа. В mock у `anomalyAnalysis` отдельно `source=mock`, `is_demo=true`. В live — source=live, is_demo=false. Предложения в `proposals[]` всегда needs_review и не разрешают изменения сами по себе. `explanation.generatedBy=OPENAI` означает добавление качественного текста к неизменному Python-шаблону; SYSTEM — только template. Фактические источники явно указаны в существующем warnings[] с code=RESULT_SOURCES: analysis=openai/mock/deterministic; calculation=deterministic; explanation=openai/template. Никаких новых полей/enum на этапе 5 не добавлено.

`calculation.analyticalHistory` хранит исходный факт отдельно от регулярного спроса и оценки stockout. `adjustments` содержит применённые бизнес-корректировки с причиной. Исторические поля и алиасы остаются; `versions.algorithm=calendar-baseline-0.1.0`. В mock промпты not-used. В live versions.openaiPrompt перечисляет подготовленные версии analysis-1.0.0/explanation-1.0.0; это версия кода промпта, а не подтверждение успешного вызова.

Арифметика: `max(0, forecastDemand + safetyStock − availableStock − eligibleInTransit)`. `availableStock` здесь **свободный остаток без поставок**; `inTransit` дублирует учтённые `eligibleInTransit` для совместимости. Не вычитайте поставки дважды. `rawRequirement` — потребность до минимума и округления; `roundedRequirement` совпадает с recommendedQuantity.

Правила календаря, полноты и округления: [../docs/mvp.md](../docs/mvp.md). Пример: 150 + 20 − 50 − 30 = 90. В `request.example.json` измените quantity первой incomingShipments на 70 — получится 50. `legacy.request.example.json` сохраняет вход этапа 2 для регрессии схемы и анализа; он неполон для надёжного расчёта и возвращает null, а не прежние фиксированные 50.

## HTTP и ограничения

- Авторизация: `Authorization: Bearer <AI_SERVICE_TOKEN>`, включая `/health` и OpenAPI. Без токена — только `AI_MODE=mock`, явный `AI_LOCAL_MODE=true` и реальный loopback peer. X-Forwarded-For не используется. Запускать без proxy headers, как указано в README.
- Content-Type: `application/json`; другой формат — 415. Excel не принимается.
- Лимит тела по умолчанию 50 MiB (52 428 800 байт), считается по реальным чанкам, даже без Content-Length; превышение — 413. Сжатые тела не распаковываются.
- По умолчанию максимум 500 товаров; превышение — 422 `PRODUCT_LIMIT_EXCEEDED` до валидации вложенных моделей.
- Общий таймаут 30 секунд включает чтение тела и асинхронную обработку; превышение — 504. Это не механизм прерывания CPU-интенсивного Python-кода: такой код потребует отдельного worker/process.
- Таймаут адаптера 15 секунд включает очередь и повторы SDK (по умолчанию 1 повтор). Максимум 2 одновременных внешних вызова на общий экземпляр `ProviderClients`, принадлежащий lifespan приложения, в одном процессе. Лимит общий для анализа и объяснения. В нескольких worker-процессах лимиты складываются. В mock внешних вызовов нет.
- Невалидный JSON — 400; неверные данные — 422; отсутствие/неверный токен — 401. Ошибки не отражают входные значения. `requestId` может быть null, если тело не разобрано или не прошло валидацию.
- Повторный `requestId` сейчас запускает новый расчёт с новым `runId`: хранения и идемпотентного кеша нет. Backend не должен считать requestId гарантией однократного исполнения будущих платных операций.

Не реализованы: пользовательский workflow согласования аномалий, экспорт и отправка заказов. Семантика полей frontend требует адаптера Go.

## Переход на единственный провайдер OpenAI

HTTP-маршруты и формат request/response сохранены. Старые внешние поля
`providers.nvidia`, `anomalyAnalysis.candidates[].nvidiaVerdict`, `versions.nvidiaPrompt`
сохранены через alias в schemas и адаптер `app/compat.py`; это только совместимость.
В текущем mock это соответственно SKIPPED/0, отсутствие кандидатов и not-used.
В health старый ключ `dependencies.nvidia` всегда disabled.
Под этими именами никогда не выдаются результаты OpenAI.
Внутренние классы и свойства используют нейтральные имена; настроек и клиента прежнего провайдера нет.

Результат mock analysis добавлен в `anomalyAnalysis.proposals`; старые candidates не переименованы. Расширения и nullable-поля нужно учесть в моделях Go до интеграции.


## Этап 5: обработка AI-сбоев без смены контракта

Live без ключа: HTTP 503 AI_NOT_CONFIGURED, без mock-подмены. Сбой анализа: anomalyAnalysis.status=FAILED и errorCode, ANALYSIS_FALLBACK, REVIEW/needs_review; вычислимое количество может остаться числовым. Сбой объяснения: EXPLANATION_FALLBACK, SYSTEM/template, количество неизменно. Провайдер OpenAI: USED при успехах, FALLBACK при смешанных исходах, FAILED при одних сбоях, SKIPPED при отсутствии вызовов. generatedExplanations считает только принятые объяснения.

Для смешанной партии общий source и source позиций сохраняют прежнее требование равенства: fallback, если был хотя бы один AI-сбой; детали этапов — в RESULT_SOURCES каждой позиции. Отключённый анализ отмечается NOT_EVALUATED и deterministic, не «аномалий нет». explanationMode=NONE отключает объяснение AI; IMPORTANT_ONLY — для BUY/REVIEW/корректировок; ALL — для всех в пределах maxAIExplanations. На позицию не более одного логического вызова каждого этапа, SDK может выполнить настроенные ограниченные повторы. При исчерпании бюджета времени остальные AI-вызовы пропускаются с явным fallback.
